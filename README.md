# tgtagbot

Телеграм-бот, который сам пишет собеседнику сообщение два раза в неделю — **в среду и в воскресенье**.

## Важное ограничение Telegram

Bot API **не позволяет боту написать человеку первым**. Пока собеседник не откроет чат с ботом
и не нажмёт **Start**, отправка в его личку невозможна — Telegram вернёт
`Forbidden: bot can't initiate conversation with a user`. Обойти это нельзя, это защита от спама.

Поэтому схема такая: собеседник один раз нажимает Start (или бот добавляется в общую группу),
`listen.py` запоминает `chat_id`, а дальше `send.py` шлёт сообщение по расписанию сколько угодно долго.

Если нужно писать человеку от **вашего личного аккаунта** без его согласия — это уже не бот, а
userbot на MTProto (Telethon), вход по номеру телефона и риск блокировки аккаунта. Здесь этого нет.

## Что внутри

| Файл | Зачем |
| --- | --- |
| `listen.py` | Долгоживущий процесс: ловит `/start` и запоминает получателей. Команды: `/start`, `/stop`, `/status`, `/test`. |
| `send.py` | Одноразовый запуск: отправляет сообщение. Его дёргает systemd timer или cron. |
| `core.py` | Конфиг, клиент Bot API с ретраями, хранилище получателей. |
| `message.txt` | Текст сообщения. Меняется без правки кода. |
| `.env.example` | Шаблон настроек: токен, дни, время, таймзона. |
| `deploy/` | Юниты systemd и пример crontab. |
| `.github/workflows/send.yml` | Расписание на GitHub Actions — бесплатный вариант деплоя. |
| `smoke_test.py` | Прогон логики без сети. |

Состояние (получатели, `last_sent`, offset getUpdates) лежит в `state.json`: локально — в корне
проекта (в git не попадает), на GitHub Actions — в `state/state.json` (коммитится, иначе между
запусками ничего не помнится).

## Установка локально

1. Создайте бота у [@BotFather](https://t.me/BotFather) → `/newbot` → скопируйте токен.
2. Настройте окружение:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt && cp .env.example .env
```

3. Впишите `BOT_TOKEN` в `.env`, а текст сообщения — в `message.txt`.
4. Проверьте, что логика цела (сеть не нужна, ничего не отправляется):

```bash
.venv/bin/python smoke_test.py
```

5. Запустите слушателя и попросите собеседника нажать Start в чате с ботом:

```bash
.venv/bin/python listen.py
```

В логе появится `зарегистрировал чат <id>`, а собеседнику придёт подтверждение с расписанием.

6. Проверьте отправку вживую, не дожидаясь среды:

```bash
.venv/bin/python send.py --force
```

Посмотреть, что уйдёт, ничего не отправляя: `.venv/bin/python send.py --force --dry-run`.

## Деплой

### Вариант A: GitHub Actions — бесплатно, без карты (рекомендуемый)

Боту нужно отправить два сообщения в неделю, то есть круглосуточный процесс не требуется —
а платят на хостингах именно за него. GitHub Actions даёт cron бесплатно: приватный репозиторий
получает 2000 минут в месяц, а один запуск съедает меньше минуты (итого ~2 минуты в месяц).

Чего не будет: `listen.py`, а значит `/start`, `/stop` и `/status` в проде не работают.
Получателя нужно зарегистрировать один раз локально (или взять `chat_id` группы) и положить в секрет.
`chat_id` группы не меняется — кроме апгрейда обычной группы в супергруппу.

1. Создайте на GitHub **приватный** пустой репозиторий (в `message.txt` ваш личный текст, а в истории — `chat_id`).
2. Запушьте проект:

```bash
git remote add origin git@github.com:USER/tgtagbot.git && git push -u origin main
```

3. В репозитории: **Settings → Secrets and variables → Actions → New repository secret**, добавьте два секрета:
   * `BOT_TOKEN` — токен от @BotFather;
   * `CHAT_IDS` — `chat_id` получателя (для группы это отрицательное число; несколько — через запятую).
4. **Actions → tgtagbot → Run workflow**, поставьте галочку `dry_run` и запустите. В логе шага «Отправка» должно быть `[dry-run] отправил бы …`. Потом то же с галочкой `force` — придёт настоящее сообщение.

Дальше воркфлоу срабатывает сам по `.github/workflows/send.yml`: `cron: "0 9 * * 3,0"` — это UTC,
то есть 12:00 MSK в среду и воскресенье. Запуск может задержаться на 5–30 минут: у GitHub cron
не гарантирует точное время. Для «привет, как дела?» это неважно, для сообщений по минутам — берите вариант B.

Отметки `last_sent` живут в `state/state.json`, который воркфлоу коммитит обратно в репозиторий.
Это же лечит и вторую особенность GitHub: в публичных репозиториях cron отключается после 60 дней
без активности, а коммит после каждой отправки эту активность создаёт.

### Вариант B: VPS с systemd — если нужен и `listen.py`

Из бесплатного здесь подходит **Oracle Cloud Always Free** (ARM-инстанс, бесплатен бессрочно, но при
регистрации потребует карту для верификации). Аналогично — always free e2-micro в Google Cloud.
AWS Free Tier не подойдёт: он на 12 месяцев, потом платно. Render, Railway и Fly.io бесплатных
тарифов под такое больше не дают — процесс либо засыпает, либо требует оплаты.

На такой машине разворачивается всё как есть, вместе со слушателем `/start`:

```bash
sudo useradd --system --home /opt/tgtagbot tgtagbot
sudo rsync -a --exclude .venv --exclude .env --exclude state.json ./ /opt/tgtagbot/
sudo -u tgtagbot python3 -m venv /opt/tgtagbot/.venv
sudo -u tgtagbot /opt/tgtagbot/.venv/bin/pip install -r /opt/tgtagbot/requirements.txt
sudo install -o tgtagbot -g tgtagbot -m 600 .env /opt/tgtagbot/.env
sudo chown -R tgtagbot:tgtagbot /opt/tgtagbot
sudo cp deploy/tgtagbot-*.service deploy/tgtagbot-send.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now tgtagbot-listen.service tgtagbot-send.timer
```

Проверка:

```bash
systemctl list-timers tgtagbot-send.timer
```

Логи: `journalctl -u tgtagbot-listen -f` и `journalctl -u tgtagbot-send -n 50`.

Вариант без systemd — `deploy/crontab.example`.

### Вариант C: PythonAnywhere Free — без карты и без git

Бесплатный аккаунт даёт одну задачу по расписанию в сутки. Этого достаточно: ставьте её на 12:00
ежедневно, а `send.py` сам промолчит во все дни, кроме среды и воскресенья. Слушателя не будет —
always-on задачи платные, так что `CHAT_IDS` прописывается руками, как в варианте A.
Учтите, что на бесплатном тарифе исходящие соединения ограничены белым списком сайтов
(`api.telegram.org` в нём есть, но проверьте перед тем, как вкладываться в настройку).

## Расписание

Дни и время заданы в двух местах, и их нужно держать согласованными:

* `deploy/tgtagbot-send.timer` — `OnCalendar=Wed,Sun 12:00` + `Timezone=Europe/Moscow`. Это фактическое время запуска.
* `.env` — `SEND_DAYS=wed,sun`, `SEND_TIME=12:00`, `TIMEZONE=Europe/Moscow`. По этому `send.py` перепроверяет день недели сам и отказывается писать в чужой день, даже если таймер настроен криво.

`Timezone=` в юните требует systemd ≥ 250 (`systemctl --version`). На более старых пересчитайте
время в UTC (12:00 MSK = 09:00 UTC) и уберите строку — `TIMEZONE` в `.env` при этом не меняйте.

Поменять на другие дни, например вторник и пятницу: `SEND_DAYS=tue,fri` в `.env`,
`OnCalendar=Tue,Fri 12:00` в таймере, затем `daemon-reload` и `restart` таймера.

## Что уже учтено

* **Не два сообщения в один день.** В `state.json` пишется `last_sent`; повторный запуск в тот же день не отправляет ничего. Поэтому `Persistent=true` в таймере безопасен: если сервер был выключен, догон сработает — но только если это всё ещё нужный день.
* **Собеседник заблокировал бота.** На `403` чат помечается неактивным и больше не дёргается, в логе видно причину.
* **Сеть и лимиты.** `429` — ждём `retry_after` от Telegram, `5xx` и обрывы — экспоненциальные ретраи.
* **Битый `state.json`** отправляется в `state.json.broken`, бот стартует с чистого состояния вместо падения.
* **Код возврата.** `send.py` возвращает `1`, если хоть одно сообщение не ушло — `systemctl status` покажет провал.

## Известные ограничения

* `listen.py` должен быть единственным, кто читает `getUpdates` по этому токену: два процесса дадут `409 Conflict`. Веб-хук у бота при этом должен быть не настроен.
* Слушатель и отправщик пишут в один `state.json` без файловой блокировки. Слушатель перечитывает файл перед записью, так что окно на гонку — миллисекунды; при вашей нагрузке (2 сообщения в неделю) этого достаточно.
* Текст один и тот же каждый раз. Если нужен список фраз по кругу или генерация — это правка `core.Config.load` и `send.py`.
